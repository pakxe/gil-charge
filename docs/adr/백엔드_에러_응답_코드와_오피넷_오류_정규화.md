# 백엔드 에러 응답 코드와 오피넷 오류 정규화

- 상태: 채택
- 작성일: 2026-08-20

## 배경

프론트에서 백엔드 오류를 안정적으로 처리하려면 HTTP status만으로는 부족하다.
사용자에게 보여줄 메시지와 프론트 분기 기준이 필요하므로, 백엔드는 일관된 public error code를 제공해야 한다.

현재 주요 실패 지점은 요청 검증, JSON 파싱, 라우팅, 오피넷 API, DB, 서버 설정 오류다.
특히 오피넷 API는 원본 오류 종류가 다양하고 일일 호출량 제한도 있으므로, 어떤 원본 오류를 프론트 계약으로 노출할지 결정이 필요했다.

## 결정 1. 실패 응답은 `{ code, message }`로 통일한다

모든 public 실패 응답 body는 아래 형태를 사용한다.

```json
{
    "code": "ERROR_CODE",
    "message": "사용자 노출 메시지"
}
```

`error`, `statusCode`, `details` 같은 필드는 기본 응답 계약에 포함하지 않는다.
필요하면 서버 내부 로그나 Sentry context로 확장하고, public API 계약은 단순하게 유지한다.

## 결정 2. public error code는 사용자 처리 단위로만 만든다

확정한 public error code는 다음과 같다.

|  HTTP | code                    | message                                   |
| ----: | ----------------------- | ----------------------------------------- |
| `400` | `MALFORMED_JSON`        | `요청 JSON 형식이 올바르지 않습니다.`     |
| `400` | `MISSING_PATHS`         | `경로 데이터가 없습니다.`                 |
| `400` | `INVALID_PATHS`         | `paths는 배열이어야 합니다.`              |
| `400` | `EMPTY_PATHS`           | `검색할 경로가 없습니다.`                 |
| `400` | `INVALID_PATH_TYPE`     | `지원하지 않는 경로 타입입니다.`          |
| `400` | `INVALID_POINTS`        | `경로 좌표 데이터가 올바르지 않습니다.`   |
| `400` | `INVALID_COORDINATE`    | `좌표 값이 올바르지 않습니다.`            |
| `400` | `INVALID_RADIUS`        | `검색 반경은 0보다 큰 숫자여야 합니다.`   |
| `400` | `RADIUS_TOO_LARGE`      | `검색 반경은 최대 5km까지 가능합니다.`    |
| `413` | `PAYLOAD_TOO_LARGE`     | `요청 데이터가 너무 큽니다.`              |
| `404` | `ROUTE_NOT_FOUND`       | `요청한 API를 찾을 수 없습니다.`          |
| `405` | `METHOD_NOT_ALLOWED`    | `지원하지 않는 HTTP 메서드입니다.`        |
| `502` | `OPINET_UNAVAILABLE`    | `유가 정보를 가져올 수 없습니다.`         |
| `503` | `DATABASE_UNAVAILABLE`  | `일시적으로 데이터를 처리할 수 없습니다.` |
| `500` | `CONFIGURATION_ERROR`   | `서버 설정 오류가 발생했습니다.`          |
| `500` | `INTERNAL_SERVER_ERROR` | `서버 내부 오류가 발생했습니다.`          |

## 결정 3. 오피넷 원본 오류는 단일 public code로 정규화한다

오피넷 API에는 인증, 파라미터, 호출량 제한, 내부 오류, 응답 구조 이상 등 여러 실패 케이스가 있을 수 있다.
처음에는 일일 300회 제한 초과를 `OPINET_DAILY_QUOTA_EXCEEDED`로 별도 노출하는 방안도 고려했다.

하지만 최종 결정은 모든 오피넷 유가 정보 조회 실패를 사용자에게 아래 하나로 노출하는 것이다.

|  HTTP | code                 | message                           |
| ----: | -------------------- | --------------------------------- |
| `502` | `OPINET_UNAVAILABLE` | `유가 정보를 가져올 수 없습니다.` |

이유는 다음과 같다.

- 사용자는 오피넷 원본 오류 종류를 직접 해결할 수 없다.
- 원본 오류를 1:1로 public code에 복사하면 프론트가 오피넷 사양 변경에 취약해진다.
- 일일 호출량 초과도 사용자 관점에서는 "현재 유가 정보를 가져올 수 없음"으로 처리하는 편이 단순하다.
- 운영자는 public 응답이 아니라 서버 로그와 추후 Sentry context로 원인을 확인하면 된다.

## 결정 4. 요청 검증 기준은 백엔드에서 명시한다

`POST /api/stations/path`는 다음 기준으로 검증한다.

- `paths`는 필수이며 배열이어야 한다.
- `paths`는 빈 배열이면 안 된다.
- `path.type`은 `pen`, `waypoint`만 허용한다.
- 각 path의 `points`는 배열이며 최소 1개 이상이어야 한다.
- 각 point의 `lat`, `lng`는 finite number여야 한다.
- `lat`은 `-90` 이상 `90` 이하, `lng`는 `-180` 이상 `180` 이하만 허용한다.
- `radiusKm`가 없으면 기본값 `3.0`을 사용한다.
- `radiusKm`는 0보다 크고 5 이하인 숫자여야 한다.

오피넷 반경 API는 최대 반경이 5000m이므로, `radiusKm > 5`는 `RADIUS_TOO_LARGE`로 응답한다.

## 결과

- 프론트는 HTTP status보다 `code`를 기준으로 안정적으로 분기할 수 있다.
- 오피넷 원본 오류 세부 사항은 public API 계약에서 숨기고, 백엔드 내부 context로만 관리한다.
- 나중에 Sentry를 붙일 때 `code`, `status`, `cause`, `context`를 이벤트 tag/context로 전달할 수 있다.
- 테스트와 프론트 에러 UI는 별도 작업으로 분리한다.

# 웨이포인트 에디터 로직과 훅 분리

- 상태: 채택
- 작성일: 2026-08-06

## 배경

웨이포인트 에디터는 지도 클릭, 선택, 삭제, 드래그 같은 UI 상호작용을 통해 웨이포인트 상태를 변경한다.
처음에는 `useWaypointEditor` 훅 안에 모든 로직을 넣을 수도 있다고 생각했다.
하지만 웨이포인트 계약에는 다음과 같은 상태 전이 규칙이 포함된다.

- 웨이포인트 추가 시 기존 선택 상태를 해제한다.
- 선택된 웨이포인트를 다시 클릭하면 선택을 해제한다.
- 다른 웨이포인트를 클릭하면 선택 대상을 변경한다.
- 드래그 중 위치는 임시 데이터이고, `dragEnd`에서만 확정한다.
- 삭제 후 선택 상태가 유효한지 다시 계산한다.
- 최대 개수를 넘으면 `OVERFLOW` 결과를 반환한다.

이 규칙들은 React나 지도 SDK의 문제가 아니라 웨이포인트 도메인의 상태 전이 문제다.

## 결정

웨이포인트 상태 전이 규칙은 순수 로직으로 분리하고, React 훅은 그 로직을 화면에서 사용하기 좋게 연결하는 역할만 맡긴다.

- 순수 로직 위치: `src/features/waypoint_editor/model/waypointEditor.ts`
- 훅 위치: `src/features/waypoint_editor/hooks/useWaypointEditor.ts`
- 순수 로직은 React, DOM 이벤트, 지도 SDK 객체에 의존하지 않는다.
- 순수 로직은 지도 제스처 용어인 `drag` 대신 도메인 용어인 `move`를 사용한다.
- 훅은 React 상태를 보관하고, model의 명령 함수를 호출한 뒤 화면이 사용할 `status`, `data`, `actions`를 반환한다.
- model 함수들은 독립 순수 함수로 작성하고, 사용 편의를 위해 `waypointEditor.addWaypoint(...)`처럼 하나의 객체에 묶어 export한다.

## 대안

### 방안 1. 훅 안에 모든 로직을 넣는다

- 장점: 파일 수가 적고 처음 구현이 단순하다.
- 단점: `useState`, `useReducer`, `useCallback` 같은 React 연결 코드와 웨이포인트 규칙이 섞인다.
- 단점: 상태 전이 규칙이 도메인 규칙을 파악하기 어렵다.

### 방안 2. 순수 로직과 훅을 분리한다

- 장점: 웨이포인트 규칙을 React 없이 읽을 수 있다.
- 장점: 훅은 React 연결부라는 책임이 선명해진다.
- 장점: 테스트가 쉬워진다.
- 장점: AI에게 "이 파일에는 상태 전이 규칙만 구현하라"고 지시하기 쉽다.
- 단점: 파일과 연결 코드가 늘어난다.
- 단점: 웨이포인트 추가 하나만 보면 구조가 과해 보일 수 있다.

### 방안 3. `createWaypointEditor` 팩토리로 model 명령을 만든다

- 장점: `createId`, `maxWaypointCount` 같은 외부 의존성을 한 번에 주입할 수 있다.
- 장점: 훅에서는 생성된 editor 객체만 사용하면 된다.
- 단점: 각 명령 함수가 실제로 필요한 의존성이 숨겨진다.
- 단점: model이 순수 함수 모음이라기보다 상태 없는 서비스 객체처럼 보인다.

### 방안 4. 독립 순수 함수를 `waypointEditor` 객체로 묶어 export한다

- 장점: 각 명령 함수가 필요한 입력과 옵션을 시그니처에 직접 드러낸다.
- 장점: 함수 구현은 독립 순수 함수로 유지하면서, 사용처에서는 `waypointEditor.addWaypoint(...)`처럼 응집된 API로 사용할 수 있다.
- 장점: 훅에서 별도 editor 인스턴스를 `useMemo`로 만들 필요가 없다.
- 단점: `addWaypoint`처럼 외부 의존성이 필요한 명령은 호출 시 옵션을 넘겨야 한다.

## 판단

웨이포인트 추가 하나만 보면 훅 안에 구현해도 충분하다.
하지만 웨이포인트 에디터 전체 계약은 선택, 삭제, 드래그, 임시 상태, 실패 결과처럼 상태 전이 규칙이 많다.

따라서 분리의 이유는 테스트 편의성만이 아니다.
주된 이유는 웨이포인트 상태 전이 규칙을 React 연결 코드와 분리해 읽기 쉽게 만들고, 계약을 구현하는 위치를 명확히 하기 위함이다.
테스트는 이 분리의 추가 이점으로 본다.

model API 구조는 `createWaypointEditor` 팩토리보다 독립 순수 함수를 `waypointEditor` 객체로 묶는 방식을 선택한다.
웨이포인트 명령은 대부분 현재 상태와 명령 입력만으로 계산된다.
외부 의존성이 필요한 명령은 일부뿐이므로, 모든 명령을 팩토리 안에 넣기보다 필요한 함수에만 옵션을 넘기는 편이 의존성을 더 명확하게 드러낸다.
다만 사용처에서는 관련 명령을 항상 함께 사용하므로, 개별 함수를 흩어서 import하지 않고 `waypointEditor` 객체로 묶어 응집된 API를 제공한다.

## 구현 규칙

- `model/waypointEditor.ts`는 순수 로직만 둔다.
    - 현재 상태와 명령 입력을 받아 다음 상태와 결과를 반환한다.
    - React hook, 컴포넌트, DOM 이벤트, 지도 SDK 객체를 import하지 않는다.
    - id 생성 같은 외부 의존성은 필요한 명령 함수의 옵션으로만 주입받는다.
    - 개별 명령은 독립 함수로 구현하되, export는 `waypointEditor` 객체 하나로 묶는다.
    - model 함수명과 상태명은 `move`, `moving`처럼 도메인 용어를 사용한다.
    - `drag`, `pointer` 같은 입력 장치 용어는 UI 컴포넌트 내부에만 둔다.
- `hooks/useWaypointEditor.ts`는 React 연결부만 둔다.
    - 내부에서 상태를 보관한다.
    - model 함수를 호출해 상태를 갱신한다.
    - 컴포넌트에는 `actions.addWaypoint(latLng)`처럼 사용하기 쉬운 API를 노출한다.
    - 반환값은 `status`, `data`, `actions` 세 그룹으로 나눈다.
- 페이지 컴포넌트는 훅을 사용한다.
    - 페이지는 model 함수를 직접 호출하지 않는다.
    - 지도 클릭 이벤트에서 받은 `LatLng`만 훅의 action으로 넘긴다.

## 훅 반환값 구조

`useWaypointEditor`는 화면이 훅을 읽을 때 역할을 빠르게 구분할 수 있도록 `status`, `data`, `actions`를 반환한다.

```ts
const { status, data, actions } = useWaypointEditor();
```

- `status`: 에디터의 현재 상태와 컨텍스트 정보를 의미한다.
    - 예: `status.statusName`은 `idle`, `selected`, `moving`
    - 화면은 이 값을 보고 삭제 버튼 표시, 이동 중 UI 표시 같은 상태 기반 분기를 한다.
- `data`: 화면에 렌더링할 데이터를 의미한다.
    - 예: `waypoints`
    - 화면은 이 값을 순회해 지도 위에 웨이포인트를 그린다.
    - 이후 드래그 기능이 들어오면 확정 데이터와 draft를 합친 "화면에 보여줄 데이터"를 제공할 수 있다.
- `actions`: 화면에서 호출할 수 있는 명령을 의미한다.
    - 예: `addWaypoint(latLng)`
    - 지도 클릭, 마커 클릭, 삭제 버튼 클릭 같은 UI 이벤트는 action을 호출한다.

한 객체에 모든 값을 평평하게 반환할 수도 있지만, 기능이 늘어나면 렌더링 데이터, 현재 상태, 명령 함수가 섞여 읽기 어려워진다.

## 결과

- 웨이포인트 상태 전이 규칙은 `model`에서 관리한다.
- model은 `waypointEditor` 객체로 묶인 독립 순수 함수 API를 제공한다.
- React 상태 보관과 화면 연결은 `hook`에서 관리한다.
- UI 컴포넌트는 `status`, `data`, `actions`만 사용한다.
- 테스트는 우선 순수 model을 대상으로 작성한다.

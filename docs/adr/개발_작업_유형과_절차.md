# 개발 작업 유형과 절차

- 상태: 채택
- 작성일: 2026-08-06

## 배경

개인 프로젝트를 진행하면서 기능을 계획한 뒤 실제 개발에 들어가려고 할 때 막히는 문제가 있었다.
예를 들어 "웨이포인트 메인 로직 구조 설계" 이슈를 만들었지만, 바로 훅을 어떻게 작성할지부터 생각하게 되었고 무엇부터 해야 하는지 선명하지 않았다.

목표는 두 가지다.

- AI에 과의존하지 않는다.
- 직관에만 의존하지 않고, 작업 유형별로 반복 가능한 절차를 따라 개발한다.

## 문제

- 막힌 원인은 훅 작성법 부족이 아니라, 요구사항을 코드 구조로 변환하는 반복 가능한 개발 절차가 없었던 것이다.
- 모든 개발 작업에 같은 절차를 적용하면 안 된다.
- "웨이포인트 메인 로직 구조 설계"는 Feature 이슈가 아니라 Design / ADR 이슈에 가까운데, Feature처럼 접근해서 막혔다.

## 결정 1. 이슈 유형을 먼저 분류한다

작업을 시작하기 전에 이슈가 해결하려는 질문과 최종 산출물을 먼저 구분한다.

| 이슈 유형    | 해결하려는 질문                                | 최종 산출물                        |
| ------------ | ---------------------------------------------- | ---------------------------------- |
| Spike        | 이 기술로 구현할 수 있는가?                    | 실험 결과, 결론, 후속 이슈         |
| Design / ADR | 어떤 구조와 규칙으로 구현할 것인가?            | 결정, 계약, 트레이드오프           |
| Feature      | 결정된 동작을 실제 사용자 흐름으로 완성했는가? | 동작하는 코드와 테스트             |
| Refactoring  | 동작을 유지하면서 구조를 개선했는가?           | 동일한 동작을 보장하는 구조 변경   |
| Bug          | 기대 동작과 실제 결과가 다른 원인은 무엇인가?  | 재현 조건, 원인, 회귀 테스트, 수정 |
| Performance  | 측정 가능한 성능 문제를 어떻게 개선할 것인가?  | 전후 측정 결과와 도입 여부 결정    |

## 결정 2. 이슈 유형별 절차를 다르게 사용한다

### Spike

- 핵심 사용자 흐름을 작성한다.
- 사용자 흐름을 기술 요구사항으로 변환한다.
- 실제 SDK 또는 라이브러리 기능과 매핑한다.
- POC를 작성한다.
- 결론과 후속 이슈를 남긴다.

### Design / ADR

- 행위 또는 사건과 관찰 가능한 결과를 기술 독립적인 문장으로 적는다.
- 어떤 동작 전후에도 항상 참이어야 하는 불변 규칙을 적는다.
- 핵심 사용자 흐름(happy path, edge case)
- 상태 전이 작성
- 데이터 모델 설계(원본, 일시적)
- react에서 어떻게 데이터를 관리할지 결정
- 필요한 기능을 함수 이름 수준으로 나열한다.
    - 외부에서 할 수 있는 명령, 외부에서 조회할 수 있는 값, 외부에 알려야 하는 결과를 구분한다.
- 함수의 계약과 반환 타입을 정한다.
- 정상, 경계, 실패 케이스를 Given-When-Then으로 적는다.
- 사용자에게 보이는 단위로 후속 Feature 이슈를 분리한다.

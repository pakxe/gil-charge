# 개발 작업 유형과 절차

- 상태: 채택
- 작성일: 2026-08-06

## 배경

개인 프로젝트를 진행하면서 기능을 계획한 뒤 실제 개발에 들어가려고 할 때 막히는 문제가 있었다.
예를 들어 "웨이포인트 메인 로직 구조 설계" 이슈를 만들었지만, 바로 훅을 어떻게 작성할지부터 생각하게 되었고 무엇부터 해야 하는지 선명하지 않았다.

목표는 두 가지다.

- AI에 과의존하지 않는다.
- 직관에만 의존하지 않고, 작업 유형별로 반복 가능한 절차를 따라 개발한다.

## 문제

- 막힌 원인은 훅 작성법 부족이 아니라, 요구사항을 코드 구조로 변환하는 반복 가능한 개발 절차가 없었던 것이다.
- 모든 개발 작업에 같은 절차를 적용하면 안 된다.
- "웨이포인트 메인 로직 구조 설계"는 Feature 이슈가 아니라 Design 이슈에 가까운데, Feature처럼 접근해서 막혔다.

## 결정 1. 이슈 유형을 먼저 분류한다

작업을 시작하기 전에 이슈가 해결하려는 질문과 최종 산출물을 먼저 구분한다.

| 이슈 유형   | 해결하려는 질문                               | 최종 산출물                        |
| ----------- | --------------------------------------------- | ---------------------------------- | ---------------------- |
| Spike       | 이 기술로 구현할 수 있는가?                   | 실험 결과, 결론, 후속 이슈         |
| Design.     | 어떤 구조와 규칙으로 구현할 것인가?           | 결정, 계약, 트레이드오프           |
| Feature     | 결정된 동작을 실제 사용자 흐름으로 완         | 성했는가?                          | 동작하는 코드와 테스트 |
| Refactoring | 동작을 유지하면서 구조를 개선했는가?          | 동일한 동작을 보장하는 구조 변경   |
| Bug         | 기대 동작과 실제 결과가 다른 원인은 무엇인가? | 재현 조건, 원인, 회귀 테스트, 수정 |
| Performance | 측정 가능한 성능 문제를 어떻게 개선할 것인가? | 전후 측정 결과와 도입 여부 결정    |

## 결정 2. 이슈 유형별 절차를 다르게 사용한다

### Spike

- 핵심 사용자 흐름을 작성한다.
- 사용자 흐름을 기술 요구사항으로 변환한다.
- 실제 SDK 또는 라이브러리 기능과 매핑한다.
- POC를 작성한다.
- 결론과 후속 이슈를 남긴다.

### Design

#### Design-base

: 모든 Design issue에 공통으로 수행되는 첫 과정

- 결정할 질문을 한 문장으로 적는다.
  ex) sdk 객체를 editor 내부까지 전달할 것인가?
- 행위 또는 사건과 관찰 가능한 결과를 기술 독립적인 문장으로 적는다.
- 어떤 동작 전후에도 항상 참이어야 하는 불변 규칙을 적는다. (필요 시 수행)
- 설계의 종류를 선택한다.
    - 상태/상호작용: 어떤 상태이며 언제 바뀌는가
    - 데이터 모델: 무엇을 저장하고 어떤 관계인가
    - 외부 경계/연동: 외부 sdk/api와 어디서 나눌 것인가
    - 책임/모듈 구조: 어떤 모듈이 무엇을 담당하는가
- 후보 방안을 생각한다(적는다).
  ex) 방안1, 방안2
- 구체적인 사례로 후보를 검증한다. (이때 중요한건 선택한 구조로 실제 상황을 끝까지 설명할 수 있는지)
    - 상태/상호작용: 핵심 사용자 흐름(happy path, edge case) -> 상태 전이 작성 -> given-when-then -> 함수 시그니처 작성
    - 데이터 모델: 데이터 인터페이스 -> 추가/수정/삭제 등의 연산
    - 외부 경계/연동(임시임 내가 해본 적 없음): 내부 로직이 실제로 필요한 값 정하기 -> 변환 경계
    - 책임/모듈 구조(임시임 내가 해본 적 없음): 앞으로 발생할 수 있는 변경 상황 예상 -> 누가 어떤 책임을 소유하는지 작성 -> 의존 방향 작성 -> 외부 공개 인터페이스 작성 ->
      ex) useWaypointEditor: React 상태와 editor 로직 연결, 컴포넌트에 명령과 조회값 제공. / 의존 방향은 React Hook -> Editor 로직, View -> Hook의 공개 인터페이스
- 결정, 근거, 부작용을 기록한다.
- 여러 개의 구현 이슈로 변환한다.

# 지도 어댑터 설계

- 상태: 채택
- 작성일: 2026-08-04

## 배경

Kakao, Naver 같은 지도 제공자들은 대부분 지도 메서드를 호출하기 위한 실제 `map` 객체를 제공한다.
지도 제공자를 쉽게 바꾸려면 화면 코드가 특정 제공자의 `map` 객체를 직접 알지 않도록 해야 한다.
따라서 지도 본체, 지도 인스턴스 접근도 공통 경계 안에서 다루기로 한다.

## 결정 1. map 객체는 useSyncExternalStore로 관리한다

- 선택한 방식: 지도 제공자의 원본 `map` 객체를 직접 노출하지 않고, 공통 `MapInstance`로 감싼 뒤 `useSyncExternalStore` 기반 저장소에 등록한다.
- 이유: 지도 객체 준비 여부에 따라 UI를 바꿀 수 있고, 여러 컴포넌트가 같은 지도 인스턴스 핸들을 구독할 수 있다.
- 방안 1: `ref`로 관리하기
    - 장점: 구현이 단순하다.
    - 단점: map 객체 준비에 따라 UI를 다시 렌더링하기 어렵다.
    - 단점: 호출마다 독립된 ref가 생기면 같은 map 객체를 공유하기 어렵다.
- 방안 2: 전역 상태 라이브러리로 관리하기
    - 장점: 전역 상태와 구독 모델을 쉽게 얻을 수 있다.
    - 단점: map 객체 하나를 위해 zustand 같은 의존성을 추가하는 것은 과하다.
- 방안 3: `useSyncExternalStore`로 관리하기
    - 장점: React의 외부 store 구독 방식과 맞고, ref의 단점을 해결한다.
    - 단점: subscribe, getSnapshot, setter 같은 보일러플레이트가 필요하다.
- 감수할 점: `useMap()`을 사용하는 코드는 map이 아직 준비되지 않은 `null` 상태를 처리해야 한다.

## 결정 2. loading/error UI는 fallback slot으로 받는다

- 선택한 방식: 각 지도 adapter가 fallback 컴포넌트를 직접 import하지 않고, `Map`의 `loadingFallback`, `errorFallback` slot으로 받은 UI를 렌더링한다.
- 이유: 지도 로딩 실패/대기 UI는 특정 지도 제공자보다 앱 화면 정책에 가깝다.
- 조건: 모든 지도 adapter에서 같은 fallback UI를 사용해야 한다.
- 방안 1: Suspense를 사용한다.
    - 장점: 선언적으로 loading UI를 표현할 수 있다.
    - 단점: 대부분의 지도 라이브러리는 렌더 중 Promise를 throw하는 방식이 아니라 script loading 상태를 콜백이나 hook으로 제공하므로 적용하기 어렵다.
- 방안 2: 모든 adapter에서 같은 fallback 컴포넌트를 import한다.
    - 장점: 구현이 단순하다.
    - 단점: adapter마다 같은 컴포넌트를 import해야 하므로 사람의 실수에 의존한다.
- 방안 3: fallback slot을 뚫는다.
    - 장점: 사용하는 쪽이 loading/error UI를 선택할 수 있다.
    - 장점: `Map` wrapper가 같은 fallback을 모든 adapter에 전달하면 통일된 UI 요구사항을 만족할 수 있다.
    - 장점: adapter는 지도 제공자의 로딩 상태만 판단하고, UI 정책은 밖으로 분리된다.
- 감수할 점: `Map`을 사용하는 쪽은 fallback UI를 넘기거나, wrapper에서 기본 fallback을 제공해야 한다.

## 결과

- 지도 제공자 원본 객체는 adapter 내부에 가두고, 앱은 공통 `MapInstance`와 공통 props로만 소통한다.
- loading/error UI는 adapter가 직접 선택하지 않고, 공통 `Map` 경계에서 slot으로 주입한다.

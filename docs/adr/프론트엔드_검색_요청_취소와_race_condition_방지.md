# 프론트엔드 검색 요청 취소와 race condition 방지

- 상태: 채택
- 작성일: 2026-08-26

## 배경

프론트엔드에는 주유소명으로 검색하는 `useSearchStationByName`과 경로 및 반경으로 검색하는 `useSearchStationByPath`가 있다.
두 훅은 요청 상태와 실패한 요청의 입력을 관리하고, View에 `search`와 `retry`를 제공한다.

현재 View는 요청 중일 때 검색 버튼을 비활성화하고 click 또는 submit handler에서도 `isLoading`을 확인한다.
재시도 역시 같은 검색 상태를 `loading`으로 바꾸기 때문에, 사용자가 다시 시도 버튼을 누른 직후 검색 버튼을 눌러 재시도 요청과 새 검색 요청을 겹치게 만드는 것도 일반적인 UI 흐름에서는 차단된다.

따라서 현재 View의 정상적인 사용자 흐름만 보면 동시 검색이 쉽게 발생하지 않는다.
그러나 이 방어는 View 구현에 의존하며 Controller인 훅 자체의 동시 호출 안전성을 보장하지 않는다.
다른 View에서 훅을 재사용하거나 코드에서 `search`를 연속 호출하면 여러 요청이 동시에 진행될 수 있다.

```text
요청 A 시작
  -> 요청 B 시작
    -> 요청 B 성공 및 B 결과 반영
  -> 요청 A 성공 및 A 결과 반영
```

이 경우 늦게 도착한 A의 결과가 최신 요청인 B의 결과를 덮어쓴다.
A의 실패가 B의 성공 뒤에 도착하면 성공 상태를 오류 상태로 바꾸고, 재시도 입력도 A의 입력으로 덮어쓸 수 있다.
컴포넌트가 unmount된 뒤에도 필요하지 않은 요청이 계속 진행되는 문제도 있다.

이 ADR은 `API 요청 계층과 실패 처리 정책`에서 정한 “Controller가 요청 취소와 race condition 방지를 책임진다”는 원칙을 검색 훅에서 어떻게 구현할지 구체화한다.

## 결정 1. 검색 훅은 latest request wins 정책을 사용한다

검색 훅에서 가장 최근에 시작한 요청만 현재 검색 상태를 갱신할 수 있다.
새 검색 또는 재시도가 시작되면 이전 요청을 취소하고, 이전 요청의 성공 또는 실패 결과는 상태에 반영하지 않는다.

View의 `disabled`와 `isLoading` 검사는 사용자 입력을 제한하는 UI 정책으로 유지한다.
Controller의 요청 취소는 호출 경로와 관계없이 상태 일관성을 지키는 별도의 안전장치로 둔다.

## 결정 2. 요청 생애주기는 Controller에서 AbortController로 관리한다

`useSearchStationByName`과 `useSearchStationByPath`는 현재 요청의 `AbortController`를 ref에 보관한다.

각 요청은 다음 순서로 실행한다.

1. ref에 이전 컨트롤러가 있으면 `abort()`를 호출한다.
2. 새 `AbortController`를 만들고 ref에 저장한다.
3. Request layer 함수에 `signal`을 전달한다.
4. 요청이 완료되어도 해당 signal이 취소된 상태라면 React 상태를 갱신하지 않는다.
5. 현재 ref가 해당 요청의 컨트롤러일 때만 `finally`에서 ref를 비운다.

Request layer의 `searchStationByName`과 `searchStationByPath`는 `AbortSignal`을 입력으로 받고 HTTP client에 전달한다.
Request layer는 signal의 전달만 책임지고, 어떤 요청을 언제 취소할지는 Controller가 결정한다.

## 결정 3. 취소된 요청은 실패 상태와 재시도 입력을 만들지 않는다

취소는 사용자에게 알릴 검색 실패가 아니라 새 요청이나 화면 이탈로 인해 더 이상 필요하지 않은 작업의 종료다.
따라서 취소된 요청은 다음 값을 변경하지 않는다.

- 검색 결과 상태
- 실패 상태와 실패 표현 정책
- 인라인 오류 또는 toast
- 실패한 요청의 재시도 입력

`REQUEST_CANCELED`의 표현 정책은 `silent`로 유지한다.
다만 취소 오류를 일반 실패 처리에 넣은 뒤 조용히 표시하는 방식이 아니라, `controller.signal.aborted`를 확인하여 실패 상태 자체를 만들지 않는다.

## 결정 4. unmount 시 진행 중인 요청을 취소한다

검색 훅은 effect cleanup에서 현재 컨트롤러의 `abort()`를 호출한다.
화면을 벗어난 뒤 필요하지 않은 네트워크 응답을 기다리지 않고, unmount된 화면의 상태를 갱신하려는 후속 작업도 중단한다.

이전 요청의 `finally`에서는 ref를 무조건 비우지 않는다.
아래처럼 현재 컨트롤러와 자신의 컨트롤러가 같은지 확인한다.

```ts
if (abortControllerRef.current === abortController) {
    abortControllerRef.current = null;
}
```

이 검사가 없으면 취소된 이전 요청의 `finally`가 새 요청의 컨트롤러 ref를 지울 수 있다.

## 고려한 대안

### View에서 loading 중 호출만 막는다

- 장점: 구현이 단순하다.
- 단점: 모든 호출자가 같은 방어 로직을 정확하게 구현해야 한다.
- 단점: 훅을 직접 또는 다른 View에서 호출하면 동시 요청을 막지 못한다.
- 판단: UX 방어로는 유지하지만 상태 일관성 보장의 근거로 사용하지 않는다.

### 요청 ID만 비교한다

- 장점: 늦게 도착한 응답이 최신 상태를 덮어쓰는 것을 막을 수 있다.
- 단점: 더 이상 필요하지 않은 네트워크 요청은 계속 실행된다.
- 판단: 상태 덮어쓰기만 막기보다 요청 자체도 취소할 수 있는 `AbortController`를 사용한다.

## 결과

- 주유소명 검색과 경로 검색에 같은 요청 생애주기 규칙이 적용된다.
- View의 구현 방식과 관계없이 최신 요청만 검색 상태를 갱신한다.
- 취소된 요청이 최신 결과, 오류 상태, 재시도 입력을 덮어쓰지 않는다.
- 컴포넌트가 unmount되면 진행 중인 요청을 취소한다.
- `REQUEST_CANCELED`는 사용자 오류로 표현하지 않는다.

## 감수할 점

- 각 검색 훅에서 컨트롤러 ref, 취소 확인, cleanup 코드를 관리해야 한다.
- 브라우저가 요청을 취소해도 이미 요청을 받은 서버의 내부 작업까지 항상 중단되는 것은 아니다.
- 취소가 정상적인 생애주기 동작이므로 오류 보고나 사용자 피드백에서 제외해야 한다.

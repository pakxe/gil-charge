# 주제

해당 컴포넌트(DrawPathStep)는 사용자가 지도 위에 원하는 위치를 선택할 수 있는 기능을 제공한다.

# 기능 목록

- 드로잉(사용자 인터렉션)
    - [ ] 웨이포인트 기능
- 현재 위치
    - [ ] 권한 허용
    - [ ] 중심을 현재 위치로 이동하기
- 데이터
    - [ ] 웨이포인트 기능으로 그려진 point[]
    - [ ] radius

# 리펙토링 평가/목표

아래 항목 중 1개 이상을 하면 리펙토링 성공이다.

- 책에서 학습했던 '인터페이스로 소통'을 적용해본다.
    - [ ] 도메인 로직을 수정했을 때 이 로직의 사용처를 수정해야하는가?
    - [ ] (중요하진 않을 것 같지만) react스럽게 캡슐화를 class가 아닌 dispatch 방식으로 해본다.
    - [ ] 구현의 변경이 외부에 영향을 주는가?

- 수정 영향도가 어떻게 개선되었는지 확인한다.
    - [ ] 도메인 로직과 UI 로직이 분리되었나?
    - [ ] 펜 기능을 추가한다고 가정하면 더 편리해졌나?
    - [ ] 다른 지도를 사용한다고 가정하면 더 편리해졌나?
    - [ ] 외부에서 내부 정보를 이용한 로직을 안쓰고 있는가?

# 개선 전 상황

- 상황: 하나의 파일에 모든 도메인 로직, 데이터, UI 로직, API 통신이 혼재되어있다
    - 문제: 수정 시 영향 범위가 넓고, 관련없어야 하는 곳도 영향 범위 내에 속하게 된다.
    - 문제: 특정 로직을 수정할 때 찾기 어렵고, 수정 부분을 파악하기 어렵다.
    - 문제: 솔직히 나는 너무 길어서 읽는 것만으로도 어렵다.

# 리펙토링 과정

- 데이터는 어떤 것?
    - waypoint[]
    - radius
    - toolType
    - 위치 허용 상태
      => 가장 작은 '위치 허용 상태'부터 영향 범위에서 떼어내보자.
- 현재 사용자 위치
    - UI와 분리하기위해 헤드리스 훅으로 분리한다. (useCurrentLocation)
    - 인터페이스로 소통하게 하기위해선 어떤 것을 return하면 좋을까...
        - 허용 상태를 UI에 사용해야하므로, UI에 필요한 상태에 대해서만 반환
        - 현재 location, location 허용 상태 2개
    - 그런데, 현재 location과 location 허용 상태를 묶어서 두면 `locationAcceptState == 'granted' && location !== null`이렇게 if걸 필요가 없으니까 어떨까. 그러나 판단을 잘 못하겠다. 뭐가 더 나을지.. 코딩에 대한 공포;;;
      => AI의 판단 방법 "권한 상태와 위치 값이 정말 하나의 상태 머신으로 묶여야 하는 도메인인가?" 로 판단. 묶게되면 '마지막으로 유효했던 latlng을 보존한다' 요구사항을 함께 만족하기가 좀 복잡시러워짐. 고로 안묶기로 결정

    - 위치 요청을 원래 useEffect안에서 했는데 분리된 훅에서도 같은 방식으로 해버리면, 위치 요청을 바로 하는 사이드 이펙트가 생긴다고 생각함. 그래서 함수로 분리하는걸 생각함
    - 위와 비슷한 이유인데, request함수에서 ref로 얼리리턴하는 것 자체도 사이드 이펙트라고 생각함, 그래서 이것도 제거하고 외부에서 핸들링 하도록 했음.
    - 함수 호출 방식으로 바뀌었으므로, acceptStatus가 loading으로 시작하는게 아니라 idle상태로 시작함. 데이터를 받아오는 중이라면 loading으로 변경
